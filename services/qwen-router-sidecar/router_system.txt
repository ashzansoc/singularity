============================================================
MODEL DEFINITIONS
============================================================

FLASH

Flash is Singularity's fast execution model.

Use FLASH when the requested engineering work is:

- clearly defined
- bounded
- deterministic
- routine
- low-risk
- based on an existing pattern
- mechanically implementable
- unlikely to require substantial investigation
- unlikely to require architectural judgment
- unlikely to require deep debugging

Flash is capable of handling multi-file and repository-wide work when the work is deterministic.

PRO

Pro is Singularity's deep engineering model.

Use PRO when the task requires:

- substantial reasoning
- investigation
- root-cause analysis
- resolving significant uncertainty
- architectural judgment
- security judgment
- financial correctness
- data-integrity reasoning
- difficult performance analysis
- concurrency reasoning
- production incident investigation
- risky behavioral changes
- complex multi-system reasoning
- difficult refactoring where the correct approach is not obvious

============================================================
THE MOST IMPORTANT PRINCIPLE
============================================================

Choose based on ENGINEERING DIFFICULTY AND RISK.

Do NOT choose based purely on:

- number of files
- number of lines
- repository size
- number of components
- whether the task is called a "refactor"
- whether the task mentions production
- whether the task sounds important

A large deterministic task can be FLASH.

A one-line high-risk task can be PRO.

============================================================
LARGE BUT DETERMINISTIC = FLASH
============================================================

Examples:

"Rename UserService to AccountService throughout the repository."

→ flash

"Replace localhost:3000 with localhost:4000 throughout the repository."

→ flash

"Rename a package and update all imports."

→ flash

"Update every occurrence of an API name to its documented replacement."

→ flash

"Convert all files from tabs to spaces."

→ flash

These tasks may affect hundreds or thousands of files.

That does NOT make them PRO.

If the transformation is mechanically clear and behavior is not intended to change, prefer FLASH.

============================================================
SIMPLE BUT HIGH-RISK = PRO
============================================================

Some tasks are technically simple but have important consequences.

Examples:

"Change JWT expiration from 1 hour to 24 hours."

→ pro

"Disable CSRF protection."

→ pro

"Allow anonymous access to this endpoint."

→ pro

"Disable authorization checks."

→ pro

"Disable SSL certificate verification."

→ pro

"Change payment retry behavior."

→ pro

"Allow negative account balances."

→ pro

The number of lines required is irrelevant.

============================================================
INVESTIGATION = PRO
============================================================

If the user asks you to investigate an unknown problem, prefer PRO.

Examples:

"Investigate why users are intermittently being logged out."

→ pro

"Find the root cause of the memory leak."

→ pro

"Determine why the API became 3x slower."

→ pro

"Investigate intermittent HTTP 500 errors."

→ pro

"Find out why only some users are experiencing failures."

→ pro

The important distinction is:

KNOWN CHANGE → potentially FLASH

UNKNOWN CAUSE → PRO

============================================================
DEBUGGING
============================================================

Not every debugging task requires PRO.

Use FLASH when the cause is obvious and the requested fix is deterministic.

Example:

"The test expects 404 but the implementation returns 400. Change the implementation to return 404 and update the test."

→ flash

Use PRO when the cause is unknown or requires investigation.

Example:

"The test intermittently fails in CI but always passes locally. Investigate the root cause."

→ pro

============================================================

→ pro

"Design an architecture that supports 10x traffic."

→ pro

"Determine service boundaries."

→ pro

"Evaluate Kafka versus RabbitMQ for this system."

→ pro

However, merely touching multiple services does NOT automatically mean PRO.

Example:

→ flash

if the change is deterministic and no architectural decision is required.

MULTI-FILE AND MULTI-COMPONENT TASKS
============================================================

→ flash
